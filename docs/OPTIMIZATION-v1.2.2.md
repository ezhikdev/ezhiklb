# EzhikLB v1.2.2: оптимизация CPU

## Что показывает ezhiklb-cpu.log

В логе 10 последовательных снимков `top` в режиме потоков (`Threads`).
Средние значения: user — 6,10%, system — 27,45%, softirq — 36,91%,
idle — 29,53%. Итого CPU занят примерно на 70,47%; в отдельных снимках
занятость составляет 66,8–74,4%. Steal и iowait в этих снимках равны нулю.

Основная работа приходится на сетевой стек ядра и HAProxy. В первом снимке
два потока HAProxy используют 72,7% и 27,3% CPU: это суммарно одно ядро,
то есть около 50% общей мощности двух vCPU. Эти значения нельзя складывать
с `%Cpu(s)`: system-время процесса уже входит в общую занятость CPU.
Потоки `ezhiklb` в логе почти не загружены.

Видны несколько групп потоков HAProxy с разными PID и временем работы.
Это совместимо с worker-процессами, которые после reload обслуживают старые
долгие TCP-соединения, но `top` не подтверждает ни родительские PID, ни причину
reload. Часть процессов может относиться к отдельной системной службе HAProxy.
Нужны `ps` и журналы именно `ezhiklb-haproxy.service`.

500 Мбит/с — информация оператора, а не измерение из этого лога. Без размера
пакетов, PPS, числа соединений, TCP/UDP-разбивки, версии HAProxy и профиля `perf`
нельзя установить стоимость обработки пакета или гарантировать конкретное
снижение CPU. Показатель панели `load1 / vCPU` также не равен занятости CPU
из `top`: в этой версии его семантика сохранена.

## Внесённые изменения

1. В defaults HAProxy добавлен `option splice-auto`. HAProxy сам выбирает
   подходящие потоки и направления для Linux splice, чтобы передавать данные
   между сокетами без копирования в userspace. Это основная оптимизация пути
   TCP-трафика. Эффект зависит от ядра, сборки HAProxy и характера трафика;
   при отсутствии подходящих условий остаётся обычная передача.
   [Официальное описание](https://docs.haproxy.org/2.2/configuration.html#4.2-option%20splice-auto).
2. Убран второй reload при `ResetConnections`: раньше HAProxy применялся
   внутри `resetConnectionState`, затем ещё раз в `Reconcile`. Теперь TCP
   применяется один раз в `Reconcile` с прежней обработкой ошибок и откатом.
   Это предотвращает лишнее поколение draining workers на таких публикациях.
   Уже существующие старые workers не завершаются принудительно.
3. `show sess` разбирается построчно непосредственно из socket. Убран полный
   дамп и массив всех его полей; IP дедуплицируются по мере чтения. Поля строки
   перебираются без отдельного массива, сохранённый IP копируется отдельно,
   чтобы не удерживать в памяти всю строку сессии.
4. `show stat` читается по одной CSV-записи с переиспользованием массива полей.
   Убраны полный ответ и `ReadAll`. Backend ищется по индексу вместо перебора
   списка destinations для каждой строки; строки неизвестных серверов
   пропускаются, чтобы не создавать ошибочный дополнительный общий счётчик.
5. Максимальный вес backend при генерации конфига вычисляется один раз на
   сервис. Время этой части генерации сокращено с O(D²) до O(D), где D — число
   destinations. Прежняя нормализация в диапазон HAProxy сохранена.

UDP/IPVS NAT, health-check и повторное применение его решений, affinity,
веса, TCP-логи, таймауты, период сбора активных IP, лимиты и API сохранены.
Новые sysctl, отключение conntrack, принудительное завершение TCP-сессий
и ограничение числа потоков HAProxy не вводились.

## Проверки и их статус

- Локально проверены diff и синтаксис изменённого установщика через `bash -n`.
- Добавлены тесты CSV-счётчиков и адресов backend, IPv4/IPv6-дедупликации,
  ошибок чтения, нормализации весов и единственного reload при reset.
- Release workflow устанавливает HAProxy и запускает `go test ./...`.
  Тест с `haproxy -c` проверяет конфиги с выключенным affinity, 900 с и 24 ч,
  а также с нормализуемыми весами 1000:1.
- В рабочем окружении отсутствуют Go и Linux/HAProxy; согласно принятому
  в `docs/TESTING.md` порядку сборка и Go-тесты оставлены GitHub Actions.
  Они ещё не запускались. Изменение нельзя считать прошедшим CI до зелёного job.
- Есть benchmark `BenchmarkParseActiveHAProxyClients` на 10 000 сессий:
  `go test ./internal/agent -run '^$' -bench ParseActiveHAProxyClients -benchmem`.
  Замеры benchmark и сравнение production CPU пока не выполнены.

Загрузить с сохранением путей:


`ezhiklb-cpu.log`, локальная `.claude/`, учётные данные и build-артефакты
в обновление не входят. Бинарники собираются GitHub Actions.

После загрузки файлов создать тег `v1.2.2`. Workflow соберёт архив
`ezhiklb_1.2.2_linux_amd64.tar.gz` и SHA-256. Перед установкой проверить
успешность job, включая тест с реальным HAProxy.

С версии 1.2.1 агент можно обновить через панель после обновления самой панели
до 1.2.2. Агент при запуске восстанавливает сохранённые сервисы и генерирует
конфиг с `splice-auto`. Полная установка доступна через `install.sh`.
С версий до 1.2.0 необходим полный установщик из-за смены TCP data plane.

## Проверка на Linux-ноде

Снять показатели до обновления и после него при одинаковом TCP/UDP-трафике,
PPS, числе соединений и размерах пакетов. Нагрузку держать несколько минут.

```bash
sudo /opt/ezhiklb/bin/ezhiklb-agent --version
haproxy -vv
sudo haproxy -c -f /var/lib/ezhiklb-agent/haproxy.cfg
grep -n splice-auto /var/lib/ezhiklb-agent/haproxy.cfg
sudo systemctl status ezhiklb-agent ezhiklb-haproxy --no-pager
sudo journalctl -u ezhiklb-haproxy --since '-10 minutes' --no-pager
ps -eo pid,ppid,lstart,pcpu,comm,args | grep '[h]aproxy'
top -b -H -d 1 -n 60 > ezhiklb-cpu-after.log
```

Если установлен `sysstat`, дополнительно снять `mpstat -P ALL 1 60`,
`sar -n DEV 1 60` и `pidstat -u -t -C haproxy 1 60`.
Сравнить общую занятость CPU по `100 - idle`, отдельно system/softirq,
скорость, PPS и CPU потоков HAProxy. Показатель load панели записать отдельно.

Проверить TCP и UDP в обоих направлениях, целостность большого TCP-потока
(SHA-256), закрепление клиента за backend, переход health-check down/up,
применение ingress IP, счётчики трафика, лимиты UDP и публикацию со сбросом.
При одном reset должен быть один reload управляемой службы HAProxy.
Для обычной публикации проверить продолжение уже открытого TCP-соединения.

При ухудшении вернуть 1.2.1 полным установщиком из релиза (self-update
предназначен для повышения версии) и повторить тот же тест. Резервные копии
полного установщика находятся в `/var/backups/ezhiklb`.
